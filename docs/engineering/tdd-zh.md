## 它做什么

`tdd` 以测试先行的方式构建功能或修复 bug —— 一次只做一个行为，通过红绿循环把代码"逼"出来。

它**不会**一开始就把所有测试写好。先批量写测试（"水平切片"）得到的只是对*想象中*行为的测试 —— 它们只检查事物的形状，对真实的变化毫无感知。`tdd` 采用的是垂直切片：一个测试，然后写刚好够让它通过的代码，再写下一个测试，每个循环都由上一个循环教给你的东西来指引。测试只针对公开接口，因此底层实现可以随意变动，而测试不必跟着动。

## 什么时候用它

输入 `/tdd` 即可调用；当任务合适时 agent 也会自动使用它 —— 比如以测试先行的方式构建功能或修复 bug，或者你说出"红绿重构"时。

当有一个具体的行为要构建、并且你想要能扛住重构的测试时，就用它。如果行为还没确定下来，先把 spec 定好 —— 用 [to-spec](https://aihero.dev/skills-to-spec)。当工作的重心其实是接口的形状而不是测试时，用 [codebase-design](https://aihero.dev/skills-codebase-design)；`tdd` 在规划阶段会调用它来借用深模块（deep module）的词汇。

## 红绿循环，一次一片

最核心的思想是**红绿循环**：写一个失败的测试（红），写刚好够让它通过的代码（绿），然后对下一个行为重复这个过程 —— 每个循环都由上一个循环教给你的东西来指引。第一个循环是一发**曳光弹（tracer bullet）**：一个能证明单条路径端到端跑通的测试，之后你再从它向外扩展。因为代码是你刚写的，你确切地知道哪个行为重要、该如何验证它 —— 你永远不会超出自己车灯照亮的范围，不会在不理解测试结构的情况下就提前定死它。

有两条规则保证测试诚实。好的测试读起来像一份规格说明（"用户可以用有效的购物车结账"），并且通过公开 API 走真实的代码路径，因此给内部函数改个名字绝不会弄坏它。期望值必须来自独立的真相来源 —— 一个已知正确的字面量、一个手工演算过的例子、spec 本身 —— 绝不能用代码计算它的方式再算一遍，否则就是一个**同义反复（tautological）**的测试：它从构造上注定会通过，却什么也没告诉你。

重构只在测试套件全绿之后才进行；红灯时绝不重构。

## 它在正常工作的标志

- 它写一个测试、让它通过，然后才写下一个 —— 而不是先写一批测试、再写一批代码。
- 测试命名的是行为，而不是内部细节，能扛住一次内部改名。
- 期望值是来自 spec 的字面量，而不是用和代码相同的方式推导出来的数字。

## 它在流程中的位置

`tdd` 是主构建链路用来写代码的红绿循环：

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

[implement](https://aihero.dev/skills-implement) 是这条链路的构建步骤，它在内部驱动 `tdd`，把每个 ticket 以测试先行的方式构建出来，然后再交接给 [code-review](https://aihero.dev/skills-code-review) —— 所以 `tdd` 是那个步骤内部的引擎，而不是一个独立的步骤。你也可以直接使用它，只要有一个具体的行为要构建、又不需要完整的 spec。它的另一个邻居是 [codebase-design](https://aihero.dev/skills-codebase-design)，`tdd` 依靠它来找到值得在其上测试的深模块接缝。当你不确定该用哪个 skill 或流程时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你指路。
